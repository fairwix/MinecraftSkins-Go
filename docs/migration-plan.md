# Анализ исходного проекта и план миграции

## Исходное приложение

Исходный репозиторий — небольшой магазин Minecraft-скинов. Это не загрузчик PNG-скинов: картинки и работа с файлами в коде не реализованы. Основной сценарий — каталог, динамический расчёт цены по BTC/USD, фиксация цены при покупке и список покупок.

### Архитектура и технологии

- ASP.NET Core Web API и .NET 9.
- Слои `Domain` → `Application` → `Infrastructure` → `WebAPI`.
- Entity Framework Core, Npgsql и PostgreSQL.
- CoinGecko `simple/price` для курса BTC/USD; кэш 60 секунд и fallback до 10 минут.
- Vanilla HTML/CSS/JavaScript фронтенд.
- Docker Compose с PostgreSQL, пятью копиями API, Nginx и стеком Prometheus/Loki/Grafana.
- xUnit-тесты покрывают прежде всего сервисы и правила приложения.

### Функциональность и HTTP-контракт

| Маршрут | Поведение |
| --- | --- |
| `GET /api/skins` | Каталог, фильтры `availableOnly`, `search`, пагинация `skip`/`take`, заголовок `X-Total-Count`; в ответе цена с учётом курса BTC. |
| `GET /api/skins/{id}` | Один скин с текущей итоговой ценой. |
| `POST /api/skins` | Создание скина, цена должна быть положительной и иметь не более двух знаков после запятой. |
| `PUT /api/skins/{id}` | Частичное обновление полей скина. |
| `DELETE /api/skins/{id}` | Soft delete. |
| `GET /api/rates/btc-usd` | Курс и метаданные источника/возраста кэша. |
| `POST /api/purchases` | Покупка по `skinId`, заголовки `X-User-Id` и необязательный `Idempotency-Key`. Цена и применённый курс сохраняются в чеке. |
| `GET /api/purchases` | История с фильтрами `mineOnly`, `skinId`, `from`, `to`, `skip`, `take`. |
| `GET /api/purchases/{id}` | Один чек покупки. |
| `/health`, `/health-ui`, `/metrics` | Проверки состояния и метрики инфраструктуры. |

Текущий `X-User-Id` — демонстрационная идентификация, а не аутентификация. В репозитории нет регистрации, паролей, JWT или провайдера учётных записей.

### Данные и связи

- `Skins`: UUID, имя (до 255 символов), базовая цена `numeric(18,2)`, доступность, даты создания/изменения, soft delete и поле конкурентного контроля.
- `Purchases`: UUID, внешний ключ `SkinId` с `RESTRICT`, итоговая цена и курс `numeric(18,2)`, источник курса, время, `BuyerId`, ключ идемпотентности.
- Индексы есть на имени/доступности скина и `SkinId`, `BuyerId`, времени, источнике и уникальном ключе идемпотентности.
- При старте загружаются четыре демонстрационных скина.

Исходная миграция хранит ключ идемпотентности с глобальным уникальным индексом, хотя бизнес-контекст связан с покупателем. Новый вариант ограничивает уникальность парой покупатель + ключ: так одинаковые клиентские ключи двух пользователей не возвращают чужой чек.

### Внешние зависимости и связанные компоненты

- CoinGecko — единственная внешняя интеграция приложения.
- Фронтенд зависит от snake/camel-контракта конкретных JSON-полей (`finalPriceUsd`, `priceUsdFinal`, `btcUsdRate`) и заголовков покупки.
- PostgreSQL хранит каталог и неизменяемый снимок стоимости покупки.
- Nginx отдаёт фронтенд и проксирует `/api`.

В репозитории также есть тестовый контроллер с ручками, которые завершают процесс, вызывают бесконечную рекурсию и принудительно убивают контейнер. Они не относятся к пользовательскому API и не переносятся в новый сервис.

## Предлагаемая Go-архитектура

```text
HTTP handler → application service → интерфейс хранилища → PostgreSQL
                            └──────→ BTC rate provider → CoinGecko
```

- `cmd/api` собирает зависимости, конфигурацию, логгер и HTTP-сервер.
- `internal/domain` содержит модели, ошибки и денежную формулу.
- `internal/service` реализует сценарии каталога/покупки и проверку входных данных.
- `internal/postgres` содержит параметризованные SQL-запросы и транзакцию покупки.
- `internal/ratestore` отвечает за таймаут, кэширование, fallback и объединение одновременных запросов курса.
- `internal/httpapi` связывает REST-маршруты с сервисами, ограничивает тела запросов и формирует Problem Details.
- `migrations` хранит прямые SQL-миграции для Goose.

Оставлены Go `net/http`, `ServeMux`, `pgx/v5` и `slog`: приложению достаточно стандартной маршрутизации, а SQL и транзакции должны быть видны напрямую. Денежные вычисления используют decimal-арифметику, а не `float64`.

## План и важные решения

1. **Инвентаризация** — выполнена по исходным контроллерам, сервисам, EF-конфигурациям, миграциям, фронтенду и тестам.
2. **Основа Go** — модуль, env-конфигурация, `slog`, connection pool, HTTP-сервер с таймаутами и graceful shutdown.
3. **Бизнес-сценарии** — каталог, фильтрация, soft delete, актуальная BTC-цена, атомарная покупка, история и идемпотентность.
4. **Инфраструктура** — SQL-миграция, PostgreSQL, multi-stage Dockerfile, Compose и OpenAPI.
5. **Качество** — unit и HTTP-тесты, опциональный интеграционный тест PostgreSQL, `go test`, `-race`, `vet`, форматирование и CI.
6. **Проверка** — сравнение контрактов, локальный запуск и проверка контейнеров; результаты отмечаются только после фактического запуска.

### Обоснованные отличия

- Уникальный ключ покупки ограничен покупателем, чтобы повтор ключа не раскрывал покупку другого пользователя.
- Цена округляется `decimal`-арифметикой до центов с банковским округлением, как `Math.Round(decimal, 2)` в исходнике.
- Покупка блокирует строку скина на время транзакции, затем проверяет доступность и фиксирует цену; это делает проверку и запись атомарными в PostgreSQL.
- Для локального запуска оставлены один backend и один reverse proxy. Несколько копий API и отдельный мониторинговый стек не дают ценности этому объёму проекта и добавляли много настроек.
- Тестовые маршруты аварийного завершения и приватный TLS-ключ из исходника исключены.

## Что стоит обсудить перед развитием

- Нужна ли настоящая аутентификация вместо демонстрационного `X-User-Id`.
- Следует ли менять `Idempotency-Key` на обязательный для покупок.
- Нужны ли публичные метрики Prometheus и отдельный health-dashboard.
- Должны ли HTTP-ошибки и сообщения валидации оставаться совместимыми с существующим фронтендом при дальнейших изменениях.
